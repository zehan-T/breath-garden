## Inquiry and decisions

### November 9 — Can a mobile browser support the core interaction?

MDN documents that `MediaDevices.getUserMedia()` can request a microphone stream after User permission, but only in a secure context such as HTTPS or localhost. This supports GitHub Pages deployment but means the full microphone loop cannot be tested from an ordinary insecure LAN URL. MDN also documents that Web Audio `AnalyserNode` exposes current waveform and frequency data without requiring the analyser output to be connected to speakers. This supports local, silent analysis without recording or uploading audio.

Decision: use `getUserMedia()` plus an `AnalyserNode`. Compute relative amplitude from time-domain samples and simple spectral characteristics from frequency-domain samples. Run a short quiet calibration before every session because microphone gain and background noise differ by phone and room.

Assumption to test: breath noise will usually be broader and less tonal than humming, but phone processing, microphone placement, cases, and room noise may make this unreliable. The prototype therefore uses mode-specific estimates selected by the User rather than claiming to automatically identify the activity.

### Scope changes

On November 9, after pitch approval, the Developer changed the first prototype in two ways:

- The primary experience became phone-only rather than equally targeting phone and desktop.
- Breathe changed from a non-microphone guided animation to a microphone interaction inspired by Nintendo blowing mechanics. Breath duration and relative strength should affect growth. Because a normal phone browser does not directly measure airflow, the product describes this as detecting breath sound.

This change strengthens the distinctive core interaction but makes microphone permission and HTTPS necessary for both current modes. The original no-microphone Breathe fallback is cut from the current version. `spec.md` contains the updated intended behavior.
